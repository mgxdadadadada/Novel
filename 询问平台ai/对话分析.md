# 平台 AI 对话分析

来源：`docs/询问平台ai/对话.txt`（789 行，2026-09-05 采集）

## 1. 结论摘要

这段对话提供了两类不同强度的证据：

1. **较强的实测证据**：平台已有原作可通过自然语言匹配；匹配成功后需要用户确认；匹配失败返回「未找到匹配的原作」；用户直接粘贴文本不会自动进入平台原作知识库；当前对话可以分析粘贴文本，但不等价于持久化入库。
2. **较弱的逆向推断**：平台可能把原作拆成角色、剧情、世界观、关系、写作等维度，并在查询时按创作目的组织回答；这些内容主要来自对话中平台 AI 对既有查询结果的二次总结，不是原始接口响应或数据库记录。

因此，这份对话**显著补充了产品行为层证据**，但不能单独证明 AIProductHub 宣传的世界观图谱、关系熵值、三幕编排或 StoryFork 已经在生产环境实现。

## 2. 已实际观察到的流程

### 2.1 已有原作的添加流程

```text
自然语言描述需要的原作
  → 平台从已有原作库匹配
  → 返回候选结果
  → 用户确认选择
  → 原作加入当前项目
  → 后续可查询角色、事件、设定等
```

证据：`对话.txt:316–407`。平台 AI 明确说「文件上传本次未演示」，并确认自然语言匹配、候选选择和加入项目。

### 2.2 匹配失败流程

对一段平台未收录的崩坏题材同人文本进行添加尝试，系统返回：

```text
未找到匹配的原作
```

证据：`对话.txt:432–490`。对话记录据此得出：平台现有匹配入口依赖已有原作库，不能通过该入口把用户粘贴文本直接入库。

### 2.3 直接粘贴文本的行为

对话记录明确区分：

| 操作 | 实际去向 | 是否进入原作知识库 |
|---|---|---|
| 粘贴文本到对话框 | 当前对话上下文 | 否 |
| 平台已有原作匹配并确认 | 项目关联的持久化原作资料 | 是（按对话描述） |
| 手动提取到备忘录 | 项目备忘录 | 是，但不是原作库深度索引 |

证据：`对话.txt:407–457`。

## 3. 原作拆解方式：证据分层

### 3.1 对话直接支持的内容

在实际项目创作中，平台 AI 曾调用原作资料查询并返回角色档案；对话记录把查询结果概括为包含：

- 外貌/识别特征；
- 性格与行为模式；
- 能力设定；
- 身份与背景；
- 与核心角色的关系；
- 按剧情阶段的角色弧线；
- 剧情梳理；
- 面向同人创作的提示。

证据：`对话.txt:694–772`。但该段是平台 AI 对此前结果的总结，原始查询响应未随文件提供，故应标为「对话转述/中等可信」。

### 3.2 平台 AI 推断、不能当作已验证实现

对话末尾提出了六阶段管线：

```text
实体识别
→ 关系抽取
→ 维度归类
→ 证据锚定
→ 衍生内容整合
→ 用途适配
```

这是一种合理的产品/算法假设，但对话中没有给出接口字段、原文 offset、任务日志、数据库 schema 或可重复调用命令。因此不能把它写成平台已经确认采用的内部实现。

## 4. 对五项宣传功能的影响

| 宣传功能 | 对话新增证据 | 当前结论 |
|---|---|---|
| 世界观拆解引擎 | 平台 AI 提到世界观、能力体系、特殊设定等查询维度 | 有内容层线索；没有架构图/逻辑校验/影响力评估实测 |
| 角色关系图谱 + 关系熵值 | 提到人物关系、关系变化时间线、CP/对立关系 | 有关系信息查询线索；没有图谱 UI、熵值计算或变量测试实测 |
| 三幕结构编排 | 实测项目资料包含「三章大纲」，不是三幕引擎 | 只能证明大纲生成，不证明三幕优化/节奏检测/情绪波形 |
| StoryFork | 对话提到添加新原作、项目资料和章节，但没有分支创建/状态快照操作 | 未观察到 StoryFork |
| 全程回查原著 | 生成项目资料时查询原作资料；写作前读取项目资料；章节生成后审校 | 有较强流程线索，但仍缺少每次工具调用的原始日志 |

## 5. 与仓库既有逆向结果的合并结论

### 可以确认

- 奇境 AI 的产品核心确实围绕「原作资料 → 角色/设定查询 → 项目资料 → 逐章创作」；
- 原作资料不是单纯聊天上下文，平台已有原作可以被项目关联和后续查询；
- 粘贴文本与原作入库是两个不同路径；
- 章节生成前后存在资料读取和审校环节；
- 章节、备忘录、角色档案、世界观资料是不同的持久化对象。

### 仍不能确认

- 用户是否能通过 Web 上传 TXT/EPUB/PDF；
- 原作解析是否由用户上传触发；
- 角色关系是否真的存为图结构；
- 是否存在关系熵值公式；
- 是否存在三幕结构优化器、节奏检测或情绪波形图；
- 是否存在 StoryFork 分支状态快照；
- 每次生成是否必然执行原作回查；
- 查询结果是否保留原文 offset 级证据。

## 6. 目录证据对本次结论的修正

单独看平台 AI 对话，会得到「文件上传未演示」；但同目录下的实拍截图和生产前端 bundle 已确认奇境 AI 网站存在 `/upload` 文件上传页，支持 `.txt/.docx/.epub`，填写标题、可选分类、选择公开/私密，并调用 `/novels/upload`。因此应区分：网站上传已确认；当前平台 AI 工具能否代替用户操作网站上传，仍未确认。详见 `用户在奇境ai平台创建的项目分析.md` §2。

## 7. 对本项目设计的直接修正

1. **不要把“粘贴原作”当作原作导入**：必须区分临时上下文、项目备忘录、原作知识库三种存储层。
2. **第一阶段必须实现已有原作匹配与项目关联**：自然语言检索 → 候选列表 → 用户确认 → 关联项目。
3. **区分网站上传与平台 AI 工具**：网站上传已验证；平台 AI 工具是否能代替用户上传仍未确认。
4. **解析产物至少设计为角色、设定、剧情摘要和关系信息**；证据引用、时间线、衍生内容整合先作为可选扩展，不能假装已确认。
5. **把“回查原著”落成可观测工具事件**：每次生成记录查询对象、命中条目、章节/来源和是否注入上下文，否则无法验证防崩效果。
